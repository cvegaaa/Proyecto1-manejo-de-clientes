Three architecture decisions already made — do not re-derive these, implement them exactly
1. Strict layered data architecture (Repository/Ports-and-Adapters, applied in miniature):

src/
  types/customer.ts                      # Customer, CustomerStatus, CustomerFormValues (types only)
  schemas/customerSchema.ts              # zod schema(s) for the form + repository boundary
  repositories/
    customerRepository.ts                # TypeScript interface (port): list, getById, create, update, remove — no implementation
    localStorageCustomerRepository.ts     # adapter implementing the interface against window.localStorage
    seedCustomers.ts                     # deterministic mock data generator (~40 customers), used to seed localStorage on first load only
  services/
    customerService.ts                    # depends ONLY on the CustomerRepository interface (constructor/module injection of the localStorage adapter at the composition point), adds simulated network latency via Promise+setTimeout, returns typed Promises
  state/
    customerReducer.ts                    # pure reducer, one action per CRUD verb + loading/error states
    CustomerContext.tsx                   # React Context + useReducer, calls customerService inside dispatched thunJosé-style effects, exposes a typed context value
  hooks/
    useCustomers.ts                       # reads context: list, search, filter, pagination helpers — this and useCustomer.ts are the ONLY data-layer imports components are allowed to use
    useCustomer.ts
  components/                             # never import repositories/, services/, or localStorage directly — only hooks/
  pages/
  App.tsx
  main.tsx
The dependency rule (state it explicitly in §7 Architecture and enforce it via file/folder convention documented in the generated CLAUDE.md, §19.2): components → hooks → Context/reducer → service → repository interface → localStorage adapter. No layer imports anything more than one hop below it. The stated reason (put it in §7 and in the generated CLAUDE.md so a future session understands why): the day a real backend exists, apiCustomerRepository.ts implements the same CustomerRepository interface, one line changes at the composition point (where CustomerContext.tsx wires up the concrete repository), and no other layer is touched.

2. Hard-delete, not soft-delete, in v1. Deleting a customer removes it from the repository/localStorage permanently, gated by a confirmation dialog (see Modal below) that names the customer and states the action is irreversible. This was a deliberate decision after evaluating soft-delete: soft-delete adds a deletedAt field, forces every list query to filter it, and demonstrates nothing to a reviewer unless paired with a trash/restore view — which is out of scope. Record this as ADR-002 in docs/decisions/ (§19, real content, not a stub): title "Hard-delete over soft-delete for v1", context, decision, consequences, and explicitly note it can be revisited if a trash view is ever built.

3. localStorage is "browser-local persistence", not a database — document this everywhere it matters. In the README's scope section, in §6 (data model) of the blueprint, and in the generated workspace/CLAUDE.md, state plainly: no backend, no database, data lives in the visiting browser's localStorage, running localStorage.clear() (or a private/incognito tab) resets to the seed data, and the repository interface above is what makes this swappable for a real API later without touching UI or state code. Write ADR-003 in docs/decisions/ capturing this as a deliberate scope decision, not an oversight.

Also write ADR-001: "Context + useReducer over an external state library (Zustand/Redux/TanStack Query)" — a single-entity CRUD app with no server to poll or cache doesn't clear the bar knowledge/capabilities/state-management.md sets for adding a store library; cite the capability file's own guidance ("ship without a store" when nothing is genuinely cross-tree beyond what Context already covers).

Data model
type CustomerStatus = 'lead' | 'active' | 'inactive';

interface Customer {
  id: string;
  name: string;
  email: string;
  phone?: string;
  company?: string;
  status: CustomerStatus;
  notes?: string;
  createdAt: string; // ISO 8601
  updatedAt: string; // ISO 8601
}
Form values = Customer minus id, createdAt, updatedAt. Zod schema: name required min 2 chars, email required + valid email format, phone optional (loose format check, no strict E.164), company optional, status enum defaulting to 'lead', notes optional max ~500 chars. No uniqueness constraint on email — keep it simple, this is not a real system.
